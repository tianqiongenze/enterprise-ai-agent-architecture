## 2. 关键取舍（对标业界）

1. **Litestar vs FastAPI**：同 Starlette 血统，框架层吞吐差 <10-20%（I/O 密集由下游决定）。选 Litestar 合理（内置 DI/DTO/OpenAPI/中间件/响应缓存，`litestar-granian` 官方整合）。真正决定性能的是 server、事件循环、DB、网络。
2. **Granian**：Rust 事件循环、省 1.5–2× 内存、内建 backpressure/respawn/max-RSS。裸 ASGI 下较 asyncio 约 +20–40%，uvloop +10-25%。**`--loop rloop` + 正确 workers/threads 比选 uvicorn 更重要**。
3. **Pulsar vs Kafka**：选 Pulsar。原生多租户(tenant/namespace/topic)、native geo-replication(多区/国家数据驻留)、独立 BookKeeper 存储+游标式订阅(多组同读)。成本是部署复杂度高于 Kafka。
4. **100万并发本质**：不是单点扛，而是**水平扩展无状态 + 队列削峰 + 有界并发**；瓶颈在 DB 连接/LLM 配额/向量 QPS。
5. **LLM 治理**：须引入推理网关(LiteLLM)——虚拟 key、按租户预算与限流、provider fallback、缓存、guardrail(PII/提示注入)。成本/Token 在网关收敛。
6. **CockroachDB**：默认 SERIALIZABLE 会抛 40001 需**显式重试**；活跃连接≈核×4，lifetime 5-30min；可评估 READ COMMITTED 降重试。
7. **Redis**：HA 用 Sentinel，超规模用 Cluster(16384 slot，异步复制无强一致)；限流用 Lua 原子脚本。

## 3. 重构方向 TOP-12

1. **量化 SLO**：定义 可用性 99.9x%、P99<200ms、并发/吞吐基线、租户隔离等级，分层各自 SLO；把"100万并发"变可度量负载模型。
2. **Granian 参数基准化**：`--workers=CPU核`（纯CPU可×2）、`--threads 4-8`、`--loop rloop`、开 HTTP/2、关 reload、用 backpressure/respawn/max-RSS；压测给出 RPS/内存/P99。
3. **无状态 API + 队列削峰 + 有界并发**：决策类走 Async API + Poll/回调；每租户并发配额（信号量）；API 不与 DB 直连长路。
4. **Pulsar 生产化**：batching(10ms/1000条)；订阅 Order=Key_Shared 保序/并行=Shared；DLQ maxRedeliverCount=3~5 + retry topic；负 ack 1s→60s 倍乘；订单幂等去重。
5. **CockroachDB 连接池+事务重试**：活跃≈核×4；AUTO_RETRY / SAVEPOINT 40001 重试协议；监控 `sql.new_conns`。
6. **全链路可观测(OTel)**：W3C tracecontext+baggage 贯通 API→队列→Worker→存储→LLM；BatchSpanProcessor；请求 ID；SLO 看板；DLQ/背压/慢查/成本告警。
7. **引入 LiteLLM 推理网关+多租户成本治理**：虚拟 key→租户预算→限流；异步流式(SSE)；成本落表；超预算降级。
8. **安全与隔离**：网关级 OIDC/JWT；CockroachDB RLS 行级隔离；密钥外置 Vault；PII 掩码+提示注入 guardrail。
9. **测试/发布工程化**：契约测试、混沌故障注入(40001/分区故障/worker崩溃)、压测门禁、多租户隔离回归、金丝雀。
10. **基础设施一致性**：IaC(Terraform/Pulumi)、GitOps(ArgoCD)、HPA/VPA 按 SLO 伸缩、版本确定性。
11. **数据治理/备份/容灾**：统一迁移管线；MinIO 冷层；Milvus DiskANN 冷热；周期全量+增量、RPO/RTO 演练。
12. **Nebula/Milvus 接入工程化**：Milvus partition-key 租户隔离+HNSW/IVF；Nebula 分区/副本+导入任务；独立连接池与超时。

## 4. 100万并发容量/架构推演

```
[CLIENT 多端]
[LB] Envoy/ALB 多区, TLS+W3C tracecontext
[API GATEWAY] 无状态 N×100 pod
    OIDC/JWT · Redis Lua 限流(每租户) · 熔断 · 幂等 · LiteLLM 网关(LLM 路由/预算/SSE)
[APACHE PULSAR] 事件总线：削峰+解耦+geo-repl
    namespace/topic 按租户·Key_Shared 保序·batching·DLQ
[WORKER 池] 无状态按队列深度伸缩, 有界并发(semaphore)
    LLM→网关(配额) · 批量写 CRDB · 向量→Milvus · 图→Nebula
[DATA] CRDB(活跃=核×4,批处理,40001重试) · Redis(缓存/限流,Cluster) · Milvus(partition隔离) · Nebula · MinIO
[OBSERVABILITY] OTel Collector → Prometheus/Grafana + Jaeger/Tempo + 日志
```

**推演要点**：100万并发≈若 QPS/并发比约10则 ~10万 RPS；无状态 pod 按单核 RPS 线性扩展(HPA+多区)。命令全入 Pulsar 天然削峰，突发吸收、Worker 按队列深度伸缩；任务降到"Worker 集群可控并发"。SQL 连接/LLM 配额/向量 QPS 为硬顶，用信号量/队列深度限流防雪崩。

## 5. 上线门槛（GO/NO-GO）

| # | 项 | 门槛 |
|---|----|------|
| GO-1 | 量化 SLO | 各层 SLO 有文档可监控验证 |
| GO-2 | 压测达标 | 目标并发下 P99/吞吐满足 SLO |
| GO-3 | 限流/熔断/幂等 | 租户限流+熔断+幂等去重，故障注入优雅降级 |
| GO-4 | 队列生产化 | Pulsar batching/DLQ/retry 齐、背压受控、DLQ 告警+重放 |
| GO-5 | DB 连接池与重试 | CRDB 池按口径、40001 重试闭环、无连接耗尽 |
| GO-6 | 全链路可观测 | Trace/Metric/Log 贯通、SLO 看板在线 |
| GO-7 | LLM 治理 | 网关落地、每租户预算/配额/成本落表 |
| GO-8 | 安全隔离 | 鉴权+RLS+RBAC+PII，密码外置无泄露 |
| GO-9 | 高可用 | LB/Granian/Pulsar/DB/Redis/向量/图多副本可切换，销毁演练 |
| GO-10 | 备份恢复 | RPO/RTO 满足、演练成功 |
| GO-11 | IaC/GitOps | 环境可复现、一键部署可回滚 |
| GO-12 | 混沌/回归 | CI 混沌+回归门禁，无发布回退 |

**NO-GO 判定**：GO-1/2/3/6/8/9 任一未达不建议上线；其余可带豁免在首个里程碑补齐。以当前约 45 分，多数 GO 项未达标，需按 §3 优先级重构后复评。

> 结论：技术栈选型(Granian+Pulsar+CockroachDB+OTel+LiteLLM)与"100万并发=水平扩展+削峰+有界并发"方向**达标且前沿**；主要缺口在 SLO 量化、LLM 推理网关、事务重试/连接池、全链路可观测、安全隔离、可运维性六块，按 §3 重构即可。
