## 四、瓶颈观察（按证据）

1. **tasks 全表列表 p95=550ms**：`ORDER BY updated_at DESC LIMIT 50` 无索引扫描 + 全行 JSON 序列化。修复方向：updated_at 索引 + 分页（`LIMIT/OFFSET`→keyset）。
2. **granian 2 workers/pod 的 CPU 上限**：spike 40VU 时 max 1.48s——单 pod 2 worker 进程是当前配置的吞吐天花板（扩副本即可线性扩容，HPA 前置条件已满足待启用）。
3. **async 入队 p95=60ms**：含 Redis LPUSH + CRDB upsert 双写——健康。
4. **NodePort 跨网络路径**：本机→175 有 ~10-20ms 固定网络开销已含在以上数字内。

## 五、结论与 SLO 建议

- **可用性**：两工具合计 **8,969 请求、0 失败**（含 40VU spike）——当前部署在受控负载下稳定。
- **SLO 建议（基于实测）**：读类 p95<600ms、async 入队 p95<100ms、错误率<1%——当前全部满足；
  tasks 列表加索引后可将最慢端点拉齐到 <200ms。
- **复跑方式**：K6 = 175 主机 `BASE=http://10.167.2.175:30080 k6 run /tmp/k6_probe.js`；
  Locust = 仓库根 `python -m locust -f tests/load/locustfile.py --headless -u 10 -r 2 -t 90s --host http://10.167.2.175:30080 --csv docs/15-data/locust`。
- **压测后清理**：压测产生的 waiting_approval 任务由审批中心按 GAP-19a 超时策略处理（earliest 过期 fail-closed）。

## 六、诚实声明

- 压测目标为 **FakeLlm 桩**（无真实模型推理）——测的是**平台吞吐/稳定性**而非模型时延；
- 强度受控（≤40VU）以保护共享集群他方业务；
- K6 thresholds 的 `rate<0.05` 通过以 k6 exit=0 为准（threshold 违反时 k6 退出码非 0）。
